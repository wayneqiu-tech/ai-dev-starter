# 06 · 监控、自动修复与定期清理

> 这一章不是给运维团队写的，是给“只有一个人 + 几个 AI”的项目写的。
> 目标不是大厂级监控，而是：**出事时你能第一时间知道，并且能退回去。**

## 1. 为什么小白也需要监控

用户不会告诉你“接口 502 了”。他们只会：

- 不再打开你的应用；
- 在群里问“怎么打不开了”；
- 或者直接卸载。

监控就是让**你先于用户知道**。不需要很复杂，先回答四个问题：

| 问题 | 靠什么回答 |
|---|---|
| 服务还活着吗？ | `/health` + 外部 uptime 监控 |
| 线上是哪一版？ | `/version` + 发布单 |
| 核心功能还能用吗？ | 一条冒烟脚本 / 合成监控 |
| 出问题去哪看？ | 结构化日志 + 错误告警 |

## 2. 最小监控：四个问题，四个动作

### 2.1 `/health`：活着

返回 200 和一小段 JSON 即可：

```json
{ "status": "ok" }
```

不要在这里查数据库/调第三方，否则依赖一抖，健康检查就全红。要查依赖，另开 `/ready`。

### 2.2 `/version`：哪一版

返回当前 `VERSION`：

```json
{ "version": "R20261106.01" }
```

发布后第一件事就是对比它和 `VERSION` 文件是否一致。

### 2.3 冒烟：核心路径还能用吗

一条脚本，跑 3–5 个检查：

- `/health` 200
- `/version` 和 `VERSION` 一致
- 登录接口能返回 token
- 一个核心只读接口 200
- 首页/登录页 200

模板见 [`../../templates/healthcheck.sh`](../../templates/healthcheck.sh)。

### 2.4 告警：出问题谁通知你

最低配：

- 一个外部 uptime 服务（UptimeRobot / Better Stack / Cloudflare 等）每 1–5 分钟探一次 `/health`；
- 一个错误告警（Sentry 免费版 / 邮件 / 飞书/钉钉/企业微信 webhook）；
- 告警内容必须带：**时间、URL、状态码、当前版本**。

> 只有日志、没有告警，等于没有监控。

## 3. 从 entropyv19 学到的

> 下面是一个真实多端项目的复盘，不点名具体业务。

### 3.1 它做对的部分（可以直接借）

| 做法 | 为什么值得借 |
|---|---|
| `/api/health` 健康接口 | 部署后、监控、负载均衡都用同一个信号 |
| 发布后固定校验脚本 | 不靠“页面能打开”，而是逐项检查 |
| 在线冒烟（登录/鉴权/核心接口/公开入口） | 覆盖“健康检查通过但业务挂了”的情况 |
| 发布前备份 + 回滚脚本 | 出事时先退，再查 |
| systemd 托管进程 | 崩溃自动拉起，比 `nohup` 可靠 |
| 版本目录/端口隔离 | 新旧版本能并存，切换只改入口 |
| 公开入口 URL 校验 | 登录/入驻等入口被 Nginx 改坏时能发现 |

### 3.2 它没做好的部分（不要照抄）

| 问题 | 后果 | 我们的改法 |
|---|---|---|
| 校验失败只打印警告，继续清理 | 线上 502，日志却写“完成” | 验证失败 = 发布失败，立即停 |
| 只有健康检查，没有指标/告警 | 用户先发现，你后知道 | 外部 uptime + 错误告警 |
| 回滚只有一层 `prev` | 连发两次版就没退路 | 保留最近 3 个版本 + tag |
| 没有 runbook | 出事时靠回忆 | 一页“告警→检查→重启/回滚→记录” |
| 上线靠手动 `export` | 换机器就失败 | 配置从环境变量读，启动校验 |
| 密钥在仓库里 | 泄露不可控 | 密钥不进库，泄露先轮换 |
| 没有自动修复 | 半夜挂了没人管 | 先做“崩溃自动重启”，不急着自动回滚 |

### 3.3 结论

**先补“验证失败即停”和“告警”，再谈自动修复。**
自动修复是最后一步，不是第一步。

## 4. 分阶段落地（别一次上全套）

| 阶段 | 时间 | 做什么 | 完成标志 |
|---|---|---|---|
| **L0 活着** | 30 分钟 | `/health`、`/version`、外部 uptime | 挂了 5 分钟内收到通知 |
| **L1 能验证** | 半天 | 冒烟脚本、发布后校验、日志 | 发布后能自动判断“成功/失败” |
| **L2 能定位** | 1–2 天 | 错误告警、请求 ID、关键指标 | 能在 10 分钟内定位到哪个接口 |
| **L3 能自愈** | 之后 | 崩溃重启、健康检查重启、条件回滚 | 常见故障不用人工介入 |

小白先做 L0 + L1。L2 再慢慢补。L3 没有前两层就不要做。

## 5. 自动修复：分级，不要一上来自动回滚

| 级别 | 动作 | 安全性 | 建议 |
|---|---|---|---|
| **A0** | 进程崩溃 → systemd/Docker 自动重启 | 高 | 默认开启 |
| **A1** | `/health` 连续失败 → 重启一次，带退避 | 中高 | 可开启，限制次数 |
| **A2** | 连续失败 → 告警，不自动改 | 高 | 默认开启 |
| **A3** | 连续失败 + 新版本 → 自动回滚 | 中 | 默认关闭，需护栏 |
| **A4** | 自动改数据/ DNS / 密钥 / 扩缩容 | 低 | 不要做 |

### A3 自动回滚的护栏（缺一不可）

1. 只回滚到**上一个验证过**的版本；
2. 该版本产物还在，且有备份；
3. 连续 3 次健康检查失败（间隔 ≥30 秒）；
4. 本次发布没有未完成的数据库迁移；
5. 每小时最多回滚 1 次；
6. 回滚后写事故记录 + 告警；
7. 默认 `AUTO_ROLLBACK=0`，要显式开启。

> 自动回滚是“止血”，不是“修复”。回滚后仍要发新版本修根因。

## 6. 一个最小可用的监控栈（小白版）

```bash
# 1) 部署后检查（复制模板后运行）
cp docs/standards/templates/healthcheck.sh scripts/healthcheck.sh
bash scripts/healthcheck.sh https://<你的域名>

# 2) 配一个外部 uptime（手机 App 就能收通知）
#    监控 URL: https://<你的域名>/health
#    频率: 1–5 分钟

# 3) 配一个错误告警（Sentry/邮件/IM webhook）
#    告警里带 version、URL、状态码

# 4) 进程托管：systemd 或 Docker 的 restart 策略
#    模板：templates/systemd-service.txt / templates/docker-healthcheck.yml
```

### systemd 的最小重启配置

```ini
[Service]
Restart=always
RestartSec=5
StartLimitIntervalSec=300
StartLimitBurst=5
```

> `Restart=always` 只能处理“进程死了”；进程活着但接口 500，它管不了。所以还需要健康检查和告警。

## 7. 故障处理 runbook（一页纸）

```
收到告警
  ↓
1. 看 /health 和 /version：是死了，还是新版本坏了？
  ↓
2. 看最近 30 分钟日志：有没有新的 ERROR/异常？
  ↓
3. 影响用户？
   ├─ 是 → 先回滚到上一个验证过的版本
   └─ 否 → 先关功能开关/限流
  ↓
4. 回滚后确认 /health、/version、核心路径
  ↓
5. 24 小时内写事故记录：现象/影响/根因/防复发
```

**原则：先回滚，再排查；不要在用户故障时现场调试。**

## 8. 定期清理：自动删除垃圾

### 8.1 为什么需要

项目跑久了，会积累：

- 构建产物（`dist/`、`build/`、`target/`）；
- 日志、临时文件、系统垃圾（`.DS_Store`）；
- 测试报告、缓存；
- 合并后没删的分支。

不清理的后果：磁盘满、clone 慢、备份变大、AI 读仓库被噪音淹没。

### 8.2 安全边界（很重要）

**会自动清理的**：

- 构建产物（未被 Git 跟踪的）；
- 日志、临时文件、系统垃圾；
- 测试报告/缓存；
- 已合并的本地分支（需显式 `--branches`）。

**永远不会自动清理的**：

- Git 跟踪的文件（脚本会检查并跳过）；
- `src/`、`docs/`、`VERSION`、发布单、tag、`.git/`；
- 密钥（泄露要**轮换**，不是删掉）。

### 8.3 用法

```bash
# 先看会清理什么（默认就是 dry-run，不删）
bash docs/standards/scripts/cleanup.sh

# 移到 .trash/<时间>/（7 天回收站，不直接删）
bash docs/standards/scripts/cleanup.sh --apply

# 定时任务用：不询问
bash docs/standards/scripts/cleanup.sh --apply --yes --purge

# 删除 7 天前的回收站内容
bash docs/standards/scripts/cleanup.sh --purge

# 删除已合并的本地分支
bash docs/standards/scripts/cleanup.sh --branches

# 打印每周定时任务的 cron 行
bash docs/standards/scripts/cleanup.sh --schedule
```

### 8.4 每周自动清理

`--schedule` 会打印一行 cron：

```
0 3 * * 1 cd "/你的项目" && bash "<cleanup.sh 的绝对路径>" --apply --yes --purge
```

- macOS/Linux：`crontab -e` 粘贴；
- 不会用 cron：把 `--schedule` 的输出复制给 AI，说“帮我装成每周自动任务”；
- Windows：任务计划程序 → 每周 → 运行 `bash docs/standards/scripts/cleanup.sh --apply --yes --purge`。

> 脚本不会自动修改你的系统定时任务；它只打印一行，你确认后再装。删除类操作不应该偷偷改你的电脑。

> 定时任务第一次跑之前，先手动跑一次 `bash docs/standards/scripts/cleanup.sh`，确认列表里没有你要的东西。

### 8.5 给 AI 的清理指令

> 按 `docs/zh/07-monitoring-and-recovery.md` 的“定期清理”：
> 先跑 `bash docs/standards/scripts/cleanup.sh` 给我看会清理什么；
> 我确认后再 `--apply`；
> 然后帮我装一个每周自动清理（先告诉我它会删什么，不要删源码/文档/发布单）。

## 9. 小白检查清单

- [ ] `/health` 和 `/version` 能访问
- [ ] 外部 uptime 监控已配置，手机能收到通知
- [ ] 错误告警已配置（至少邮件/IM）
- [ ] 进程有自动重启（systemd/Docker）
- [ ] 发布前有备份，回滚命令能跑
- [ ] 每周自动清理已开启（先 dry-run 确认）
- [ ] 有一页 runbook：告警→检查→回滚→记录

## 10. 一句话

**监控不是“看到更多图表”，而是“比用户先知道”。**
自动修复不是“让 AI 乱动”，而是“把最常见的崩溃，用最保守的方式拉起来”。
