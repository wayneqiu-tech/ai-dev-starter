# 00 · 为什么需要这套规范

> 这一章讲“为什么”，不讲“怎么做”。如果你只想快速上手，直接看 [`../06-adoption.md`](06-adoption.md)。

## 1. 一个真实的起点

这套规范不是坐在办公室里想出来的。它来自一个真实的多端项目：有 Web 后台、有桌面客户端、有后端 API、有多个外部集成；开发过程中换过好几轮“版本”，也用过好几个 AI 工具。

项目最后能跑，但留下了一堆工程债：

- 同一个项目存在好几套“版本”，没人能立刻回答“线上现在跑的是哪一版”；
- 同一个配置在三个地方三个值，按文档操作反而会出错；
- 没有可追溯的 Git 历史，改错了只能靠复制文件夹回退；
- 发布靠手工脚本，验证失败只打印一句警告，然后继续清理；
- 回滚只有“上一份文件”一层，而且回滚脚本还会顺手改数据；
- 密钥直接躺在仓库里，`.gitignore` 写了但历史文件还在；
- 文档有四五份，互相打架，新人和 AI 按哪份做都可能错。

后来把这些事故逐条复盘，一共 **47 条**。把它们去重、归类，得到 **30 个可复用的模式**（见 [`../../pitfalls/zh.md`](../../pitfalls/zh.md)），再往上抽象，就是这套规范。

> 所以这套规范不是“最佳实践大全”，而是一份**病历变成的守则**。

## 2. 五个反复出现的循环

47 条事故不是孤立的，它们背后是 5 个循环。不打断循环，写再多规则也会退回去。

### 循环 1：复制

怕改坏 → 复制一份文件夹 → 两份都改了 → 不知道哪份对 → 再复制一份。

**后果**：版本永远说不清，磁盘里全是“看起来都对”的代码。

**打断方式**：一个项目一个仓库、一个工作目录；版本用 tag，不用文件夹。

### 循环 2：配置

改端口/路径只改一处 → 联调失败 → 直接上服务器手工改 → 服务器和仓库更不一致。

**后果**：环境漂移，线上和本地行为不同，排查从“配置对不对”开始。

**打断方式**：一个配置真源；启动时打印生效值；部署后校验实际值。

### 循环 3：测试

赶时间跳过测试 → 上线出错 → 紧急回滚 → 回滚只有一层 → 修不干净 → 下次更不敢测。

**后果**：发布变成赌博，回滚变成二次事故。

**打断方式**：门禁前置；回滚目标必须是验证过的版本；回滚只回代码，不回数据。

### 循环 4：文档

文档写一套、脚本做另一套 → AI 按文档做错 → 再补一份新文档 → 三份互相矛盾。

**后果**：文档失去信任，最后没人看；AI 学到的是错的。

**打断方式**：文档入 Git；一个入口；文档和代码同一个 PR；废弃文档要留指路牌。

### 循环 5：顺手

一个需求顺手改端口/依赖/配置 → 出问题无法单独回滚 → 只能全部重来。

**后果**：提交越来越大，风险越来越集中，review 越来越形式化。

**打断方式**：一次只做一件事；一个提交只回滚一件事；大改拆小。

> 这五个循环，比任何单条规则都重要。规则可以裁剪，循环必须打断。

## 3. 三条底层原则

### 原则 1：一个事实源（Single Source of Truth）

同一个信息，只能有一个“算数”的地方。

- 版本号：`VERSION` 文件，不是文件夹名，不是 `package.json`。
- 配置：一份 `.env.example` + 环境变量，不是每个环境复制一份。
- 文档：README 的文档表，不是散落十份“最新版”。
- 线上状态：部署清单 `manifest.json`，不是“我记得上次发的是……”。

**自检**：随便指一个信息，问“它的唯一来源在哪？”答不上来就是坑。

### 原则 2：小步可回退（Small & Reversible）

每次改动小到能说清、能测、能单独回滚。

- 一个提交只做一件事。
- 一个分支活不过 7 天（可配置）。
- 一次发布只改一个主题。
- 回滚目标必须是“验证过的版本”，不是“上一份文件”。

**自检**：如果这次改动出问题，我能在 5 分钟内只回退它吗？

### 原则 3：机器可检查（Machine-checkable）

能被脚本/CI 检查的，不靠自觉。

- 版本格式、tag、发布单 → 脚本查。
- 密钥、大文件、构建产物 → CI 查。
- 测试、构建、健康检查 → 流水线跑。

**自检**：这条规则能不能写成一条命令？能，就写；不能，就简化到能。

## 4. 它是什么，不是什么

**它是**：

- 一套默认基线，给独立开发者、公民开发者、小团队。
- 一份你和 AI 之间的合同：先读什么、做什么、不许碰什么、怎么证明做完了。
- 一套可检查的规则，不靠“我记得”。
- 一个可以 fork、裁剪、加严的起点。

**它不是**：

- **不保证产品成功**。它降低流程型事故，不验证业务规则、架构、支付、打印、性能、合规。
- **不是架构/产品文档**。它不教你怎么设计租户、怎么定价、怎么建表。
- **不替代 Lint/格式化**。风格交给工具；这套管协作方式和代码底线。
- **不是认证**。项目可以更严；更松要写清原因并接受风险。

> 如果有人告诉你“照这个做就没问题了”，那是不负责。规范降低概率，不消除风险。

## 5. 给谁用

| 你是谁 | 你会得到什么 |
|---|---|
| 独立开发者 | 不再靠记忆发布；版本、回滚、密钥有底 |
| 公民开发者 | 一套看得懂的 Git/发布/回滚流程，不要求懂底层 |
| 1–5 人小团队 | 多个 AI 工具、多个人，共用一套规则 |
| 开源维护者 | 人类和 AI 贡献者按同一套标准提交 |

你不需要懂 Git 内部原理，也不需要会写 CI。你只需要：

1. 一个项目；
2. 30 分钟；
3. 愿意先做“最小五件事”（见 [`../06-adoption.md`](06-adoption.md)）。

## 6. 怎么用这套规范

### 路径 A：新项目

1. 读 [`../06-adoption.md`](06-adoption.md) 的“30 分钟开箱”。
2. 用 `scripts/init-project.sh` 生成骨架。
3. 按 `standard.conf` 选一档预设。
4. 第一次发布前，跑 `preflight --release`。

### 路径 B：老项目，已经很乱

1. 先读 [`../06-adoption.md`](06-adoption.md) 的“从混乱迁移的 7 步”。
2. 不要重写历史；先冻结、建仓、打基线 tag。
3. 先补“版本 + 回滚 + 密钥”三件事，再补别的。

### 路径 C：只想抄清单

直接看 [`../06-adoption.md`](06-adoption.md) 的检查清单，或者 [`../../CHEATSHEET.zh.md`](../../CHEATSHEET.zh.md)。

## 7. 一个请求

这套规范是 v1.0，不是终点。它一定有不适合你项目的地方。

- 觉得太严：先降档（strict → standard → minimal），不要直接无视。
- 觉得太松：往上加，但写清“为什么加”。
- 踩到新坑：提一个 issue，附上“现象/危害/你怎么解决的”。

规范的生命力不在写得多全，而在**有人真的用它，并且它真的拦住过事故**。
