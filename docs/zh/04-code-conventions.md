# 03 · 代码约定

> 这一章不规定“用 Tab 还是空格”，那是格式化工具的事。它规定的是**人和 AI 都必须守的代码底线**：怎么命名、怎么拆、怎么报错、怎么不留坑。

## 1. 为什么 AI 时代更需要代码约定

AI 会模仿仓库里已有的代码。

- 仓库里到处都是 `data1`、`tmp`、`handle2`，AI 就会继续生成 `data2`。
- 仓库里到处是空 `catch`，AI 就会觉得“吞掉错误”是项目风格。
- 仓库里有一个 800 行的函数，AI 就会在里面再塞 200 行。

**代码约定不是为了好看，是为了让 AI 有东西可模仿，让人有东西可 review。**

## 2. 六条底线

### 2.1 可读性优先

代码是写给人看的，顺便给机器执行。

- 名字要能读懂：`remainingAttempts` 而不是 `n`。
- 少用“聪明”的写法：一行嵌套三元表达式，不如三行 `if`。
- 不写“只有作者懂”的缩写，除非是领域通用（`id`、`url`、`http`）。

### 2.2 小单元

- 一个函数只做一件事。
- 一个文件只放一个主题。
- 函数超过 50 行、文件超过 400 行，先想想能不能拆。
- 嵌套超过 3 层，用提前返回（early return）压平。

### 2.3 显式优于隐式

- 不靠“全局变量碰巧存在”。
- 不靠“配置默认值碰巧对”。
- 不靠“这个函数应该不会返回空”。
- 类型、参数、返回值，能让它明确就明确。

### 2.4 错误要响

- 失败要报错，不要静默返回 `null` / `[]` / `false`。
- 不能处理的错误，向上抛，不要吞。
- 错误信息要带上下文：哪个操作、哪个 ID、期望什么。

### 2.5 不留死代码

- 注释掉的代码删掉（Git 里有历史）。
- 不用的函数、变量、导入删掉。
- `TODO` 要写清“为什么、谁、什么时候处理”，否则就是垃圾。

### 2.6 依赖要有理由

- 新增依赖前问：能不能用标准库？体积多大？许可证？维护状态？
- 不为一个 5 行的功能引入一个框架。
- 锁文件（`package-lock.json` / `poetry.lock`）必须入库。

## 3. 命名

| 对象 | 规则 | 好例子 | 坏例子 |
|---|---|---|---|
| 文件 | 小写 + 短横线或项目约定 | `user-profile.ts` | `UserProfileFinal2.ts` |
| 变量 | 名词，能读懂 | `pendingOrders` | `list1`、`tmp` |
| 函数 | 动词开头 | `calculateTotal()` | `total()`、`doIt()` |
| 布尔 | `is/has/can/should` | `isReady`、`hasAccess` | `flag`、`status` |
| 常量 | 大写 + 下划线（按语言） | `MAX_RETRIES` | `max` |
| 类/类型 | 名词，单数 | `OrderService` | `OrderManagerHelperUtil` |

规则：

- 不要用拼音（除非是业务专有名词且团队都懂）。
- 不要用无意义前缀：`IUser`、`CUser`、`BaseImpl`。
- 同一概念只用一个词：不要同时用 `user`、`member`、`account` 指同一个东西。

## 4. 函数与文件

### 4.1 函数

```js
// 好：一个函数只做一件事，错误显式
function parsePrice(raw) {
  const value = Number(raw)
  if (!Number.isFinite(value) || value < 0) {
    throw new Error(`Invalid price: ${raw}`)
  }
  return value
}
```

```js
// 坏：解析 + 校验 + 写库 + 发通知，混在一起
function handlePrice(raw, db, mailer) {
  const v = Number(raw)
  db.save(v)
  mailer.send('price updated')
  return v
}
```

- 参数超过 4 个，考虑用对象。
- 不要用布尔参数控制分支（`render(true, false)` 谁也看不懂）。
- 副作用（写库、发请求、改全局）放在函数名里体现：`saveOrder`、`sendEmail`。

### 4.2 文件

- 一个文件一个主题；文件名和默认导出对得上。
- 导入顺序：标准库 → 第三方 → 项目内（按工具自动排序）。
- 不要在一个文件里放三个不相关的类，只因为“方便”。

## 5. 注释

注释解释**为什么**，不解释**是什么**。

```js
// 好：解释取舍
// 这里必须用 UTC：数据库存的是 UTC，展示层再转本地时区。
const timestamp = new Date().toISOString()
```

```js
// 坏：复述代码
// 把 timestamp 设为 ISO 字符串
const timestamp = new Date().toISOString()
```

规则：

- 不写“作者是谁、哪天改的”（Git 有）。
- 不写注释掉的代码。
- `TODO` 格式：`// TODO(2026-12-31, @name): 删除旧接口`。
- 公共 API、复杂算法、非显然的边界，必须有注释。

## 6. 错误处理

### 6.1 不要吞错误

```js
// 坏
try {
  await saveOrder(order)
} catch (e) {
  // ignore
}
```

```js
// 好
try {
  await saveOrder(order)
} catch (error) {
  logger.error('saveOrder failed', { orderId: order.id, error })
  throw new Error(`Failed to save order ${order.id}`, { cause: error })
}
```

### 6.2 错误信息要能定位

- 带上“做了什么、哪个对象、期望什么”。
- 不要把密钥、token、完整用户数据写进错误信息。
- 面向用户的错误和面向日志的错误分开：用户看“保存失败，请重试”，日志看堆栈和 ID。

### 6.3 不要用异常做正常流程

- “找不到”是正常情况，返回 `null` / `undefined` 并在类型上体现。
- “参数非法”是异常，直接抛。
- 不要用 `try/catch` 包住整个函数来“防止崩溃”。

## 7. 日志

- 用结构化日志（JSON 或 key-value），不要拼字符串。
- 级别：`debug`（开发）、`info`（关键事件）、`warn`（可恢复异常）、`error`（需要人看）。
- 每条日志带上下文：请求 ID、用户 ID（脱敏）、操作、耗时。
- **绝不**记录：密码、token、密钥、完整身份证/手机号/银行卡、儿童敏感信息。

## 8. 配置

- 不硬编码：端口、域名、路径、开关、密钥。
- 配置从环境变量/配置文件读，启动时校验必填项。
- 默认值只能是“本地开发用、明显不安全”的值，且启动时打印警告。
- 新增配置必须同步 `.env.example`，并在发布单写清。

```js
const required = ['DATABASE_URL', 'API_KEY']
const missing = required.filter((key) => !process.env[key])
if (missing.length) {
  console.error(`Missing env: ${missing.join(', ')}`)
  process.exit(1)
}
```

## 9. 依赖

- 新增依赖前：标准库能不能做？体积？许可证？最近一年有没有维护？
- 不引入“全家桶”只为用一个函数。
- 锁文件入库；升级依赖单独提交（`build:`）。
- 删除依赖也要提交，不要只删 `import`。
- 定期看漏洞告警；高危漏洞限期修。

## 10. 测试

### 10.1 最少测什么

1. **核心路径**：用户最常做的那件事。
2. **边界**：空值、0、负数、超长、重复。
3. **错误路径**：网络失败、权限不足、超时。
4. **回归**：每修一个 bug，补一个能复现它的测试。

### 10.2 测试怎么写

- 一个测试只验证一个行为。
- 测试名说清“什么条件下、期望什么”：`rejects negative price`。
- 单元测试不连真实网络/数据库；集成测试单独分层。
- 测试必须可重复：不依赖当前时间、随机数、执行顺序。
- 不写“为了覆盖率”的空测试。

### 10.3 AI 写测试的坑

- AI 可能写“断言当前实现”的测试，而不是“断言需求”。
- AI 可能为了让测试过，把断言改松。
- AI 可能 mock 掉真正要测的东西。
- 发现这三种，退回重写。

## 11. AI 生成代码的额外检查

AI 写代码有几个高频问题，review 时重点看：

| 问题 | 表现 | 怎么防 |
|---|---|---|
| **编造 API** | 调用了不存在的函数/参数 | 查官方文档；跑类型检查/测试 |
| **假导入** | `import { x } from 'some-lib'`，但包里没有 | 构建/测试会报错；别忽略 |
| **静默降级** | 出错就返回空数组/默认值 | 要求显式报错或日志 |
| **复制粘贴** | 从旧项目抄一段，带旧配置/旧路径 | 搜硬编码；问“这段为什么需要” |
| **过度抽象** | 一个小功能拆 8 个文件 | 先能跑，再抽象；别为未来设计 |
| **“应该能跑”** | 没运行就说完成 | 要求命令 + 输出 |
| **改测试** | 把失败断言改成通过 | 测试是需求，不是障碍 |

## 12. 不要在这份规范里规定的东西

- **格式化**：Tab/空格、引号、行宽 → 交给 Prettier/Black/gofmt。
- **框架选型**：React/Vue/Svelte → 看项目和团队，不在这份规范里。
- **目录结构**：不同语言/框架不同 → 在 `AGENTS.md` 里写清本项目的。
- **命名大小写**：按语言社区习惯（JS `camelCase`、Python `snake_case`）。

> 这份规范管“不可协商的底线”和“AI 协作方式”，不管“个人口味”。

## 13. 一页纸代码 review 清单

- [ ] 命名能读懂，没有 `tmp` / `data1` / `doIt`
- [ ] 函数 <50 行，文件 <400 行，嵌套 <3 层
- [ ] 没有注释掉的代码、没有无用导入
- [ ] 错误没有被吞；错误信息能定位
- [ ] 没有硬编码 IP/端口/路径/密钥
- [ ] 新配置进了 `.env.example`
- [ ] 新依赖有理由，锁文件已更新
- [ ] 核心路径/边界/错误路径有测试
- [ ] AI 没有编造 API、没有改测试断言
- [ ] 能说清“出问题怎么回滚”
