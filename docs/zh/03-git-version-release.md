# 02 · Git、版本、发布

> 这一章解决三个问题：**改动怎么隔离、版本怎么定、发布怎么退**。
> 所有命令都以默认的日期号方案为例；用 SemVer 时把版本号换掉即可。

## 1. 分支：主干 + 短分支

### 1.1 默认模型

只有 `main` 是长期分支，其他都是“用完就删”的短分支。

```
main ──●────●────●────●────●──→  永远可发布
        \        /    \      /
         feat/x  ●      fix/y ●       ≤7 天，合完即删
```

| 分支 | 从哪来 | 活多久 | 干什么 | 合到哪 | 合并方式 |
|---|---|---|---|---|---|
| `main` | — | 永久 | 随时可发布 | — | — |
| `feat/<slug>` | `main` | ≤7 天 | 新功能 | `main` | Squash |
| `fix/<slug>` | `main` | ≤3 天 | 修 bug | `main` | Squash |
| `docs/<slug>` | `main` | ≤3 天 | 文档 | `main` | Squash |
| `chore/<slug>` | `main` | ≤3 天 | 依赖/配置/杂务 | `main` | Squash |
| `refactor/<slug>` | `main` | ≤7 天 | 重构（不改行为） | `main` | Squash |
| `test/<slug>` | `main` | ≤3 天 | 补测试 | `main` | Squash |
| `release/<版本>` | `main` | ≤3 天 | 冻结验收（可选） | `main` + tag | Merge |
| `hotfix/<版本>-<slug>` | 出问题的 **tag** | ≤1 天 | 线上紧急修复 | `main` + 新 tag | Merge |
| `wip/<日期>-<slug>` | `main` | ≤7 天 | 半成品备份，不合并 | 转正或删除 | — |

> **为什么一个人也要分支**：分支是“隔离未完成品”的工具，不是给别人看的。你在 `feat/` 上改坏了，`main` 还是好的，随时能发版。

### 1.2 命名规则

```
<类型>/<英文小写 slug>
```

- slug 用英文小写 + 数字 + 短横线：`feat/voice-fallback`、`fix/login-500`。
- 2–40 个字符；不要中文、空格、下划线、日期前缀（日期只放在 `wip/` 里）。
- 一个分支只做一件事；分支名就是这件事的标题。

正则（可直接用于 CI/钩子）：

```regex
^(main|(feat|fix|docs|chore|refactor|test|perf|build|ci)/[a-z0-9][a-z0-9.-]{1,39}|release/R20[0-9]{6}\.[0-9]{2}|hotfix/R20[0-9]{6}\.[0-9]{2}-[a-z0-9-]{2,30}|wip/[0-9]{8}-[a-z0-9-]{2,30})$
```

### 1.3 生命周期

1. **切**：`git switch main && git pull && git switch -c feat/xxx`
2. **做**：小步提交（见 §2），每完成一小块跑一次测试。
3. **同步**：每天 `git fetch && git rebase origin/main`（只 rebase 自己的分支）。
4. **自检**：`preflight` + 测试 + 构建全过。
5. **合**：开 PR（哪怕自己合），写清“为什么/验证了什么/怎么回滚”。
6. **删**：合并后立刻删分支（本地 + 远程）。
7. **超期**：超过 7 天没合的分支，要么拆小合入，要么转 `wip/` 并写清原因。

### 1.4 一个人怎么做 review

没有人 review，就用“流程”代替“另一个人”：

1. **隔夜 review**：当天写的代码，第二天早上再看一遍 diff。80% 的低级问题能自己发现。
2. **AI 二审**：让另一个 AI 会话读 diff，只问三个问题：这改了什么？有没有超范围？有没有安全问题？
3. **强制自问**（贴到 PR 描述里）：
   - 这个改动能用一句话说清吗？
   - 如果现在回滚，会带走别的东西吗？
   - 有没有硬编码、密钥、调试代码？
   - 测试/构建真的跑了吗？输出在哪？
4. **diff 阈值**：超过 400 行（或 20 个文件）就拆。

### 1.5 特殊操作

| 操作 | 正确做法 | 禁止 |
|---|---|---|
| 看历史版本 | `git worktree add ../look/<tag> <tag>` | 在主工作区 `checkout <tag>` 后提交 |
| 临时存代码 | `git stash push -m "说明"`，24 小时内处理 | 无说明 stash、长期不清理 |
| 同步 main | 在自己的分支 `git rebase origin/main` | 在 `main` 上 rebase 别人的分支 |
| 撤销已推送的提交 | `git revert <sha>`（产生新提交） | `git reset --hard` + `push -f` 公共分支 |
| 改提交信息（未推送） | `git commit --amend` | 改已推送且别人在用的提交 |

### 1.6 可选：什么时候加 `release/` 分支

只有这三种情况需要：

1. 发布前要冻结 1–3 天做验收，期间 `main` 继续开发。
2. 需要同时维护两个版本（如 v1 修 bug、v2 开发中）。
3. 应用商店/客户验收要求“提交后不能再变”。

否则不要加。`release/` 只允许修 bug，不允许加功能；发布后 24 小时内合并回 `main` 并删除。

### 1.7 分支禁止清单

- ❌ `develop`、`develop2`、`dev-new`、`test`、`backup` 这类长期分支（除非团队明确采用 Git Flow）。
- ❌ 用分支名当备份：`main-20261106`、`before-refactor`。
- ❌ 在 `main` 上直接改代码再提交（哪怕只有一个人）。
- ❌ `push --force` 到 `main` 或别人的分支。
- ❌ 一个分支混多个不相关的功能。

## 2. Commit：一条只做一件事

### 2.1 判断标准

**能用一句话说清，且回滚它不会带走别的东西。**

- ✅ `fix(login): 登录失败时不再清空整个表单`
- ❌ `fix: 修了一些问题`（说不清）
- ❌ `feat: 新首页 + 升级依赖 + 改端口`（三件事）

大改拆成多个提交：**先重构（不改行为）→ 再加功能 → 再改文档**。这样出问题能只回退其中一步。

### 2.2 格式

```
<type>(<scope>): <subject>

<body：为什么改、改前什么问题、有什么取舍>

<footer：Refs #12 / BREAKING CHANGE: ... / Co-authored-by: ...>
```

| 部分 | 规则 |
|---|---|
| `type` | 必填，见下表 |
| `scope` | 可选，模块名：`login`、`api`、`docs`、`deploy` |
| `subject` | 必填，≤50 字，动词开头，句末不加句号；中文可以 |
| `body` | 建议填，写“为什么”，不写“改了哪些文件”（diff 已经写了） |
| `footer` | 关联 issue、破坏性变更、AI 协作署名 |

### 2.3 type 表

| type | 用于 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat(voice): 支持低置信度重说` |
| `fix` | 修 bug | `fix(api): 修复超时未释放连接` |
| `docs` | 只改文档 | `docs: 补充回滚步骤` |
| `refactor` | 重构，不改行为 | `refactor(core): 拆分提示阶梯函数` |
| `perf` | 性能优化 | `perf(web): 首屏减少一次请求` |
| `test` | 只改测试 | `test(core): 补边界用例` |
| `build` | 构建/依赖 | `build: 升级 vite 到 5.4` |
| `ci` | CI 配置 | `ci: 增加密钥扫描` |
| `chore` | 杂务（不影响产物） | `chore: 清理临时脚本` |
| `revert` | 撤销某次提交 | `revert: 撤销 feat(voice) ...` |

> `feat` / `fix` 会进 CHANGELOG；`chore` / `ci` / `test` 通常不进。

### 2.4 好例子 / 坏例子

**好**：

```
fix(deploy): 校验失败时停止后续清理

之前 verify 失败只打印警告，清理脚本继续执行，可能删掉回滚所需的
system.prev。现在失败即退出，并把清理放到验证通过之后。

Refs #42
```

**坏**：

```
update
```

```
修复bug，优化代码，更新配置
```

```
改了很多文件
```

### 2.5 AI 生成代码的提交规则

1. **人必须读懂每一行**再提交；读不懂就让 AI 解释，解释不清就不合。
2. 在 `AGENTS.md` 授权时，AI 可以在**任务分支上**执行 `git switch -c`、`git add`、`git commit`；未经明确同意不得合并到 `main`、push、打 tag、部署，也不得直接在 `main` 上提交。
3. AI 参与的提交，在 footer 注明：

   ```
   Co-authored-by: <AI 工具名> <noreply@example.com>
   ```

4. AI 一次生成超过 400 行，先拆再提交。
5. AI 不得为了让测试通过而修改测试断言、跳过测试、删日志；发现就回退。

### 2.6 提交模板与钩子（可选但推荐）

```bash
# 使用模板
git config commit.template docs/standards/templates/commit-message.txt

# 提交信息格式检查（.git/hooks/commit-msg）
#!/usr/bin/env bash
msg_file="$1"
head -1 "$msg_file" | grep -qE '^(feat|fix|docs|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?: .{2,50}$' \
  || { echo "提交信息格式不对，见 docs/standards/03-git-version-release.md"; exit 1; }
```

### 2.7 常见问题

- **WIP 提交可以吗？** 可以，但只能在自己的分支；合并前 squash 成有意义的提交。
- **合并提交要不要保留？** 单人项目不需要；`release/`、`hotfix/` 合并时保留。
- **一个提交多大合适？** 以“能独立回滚”为准，通常 <300 行；超过 400 行考虑拆。
- **用中文还是英文？** 团队统一即可；开源项目建议英文标题，正文中英都可。

## 3. 版本：一个真源

### 3.1 先选方案

#### 方案 A：日期号 `R<YYYYMMDD>.<NN>`（默认）

```
R20261106.01
R20261106.02     ← 同一天第二次发布
R20261107.01     ← 第二天从 .01 重新开始
```

| 部分 | 规则 |
|---|---|
| `R` | 固定大写，不带 `v` |
| `YYYYMMDD` | **发布当天**的日期（项目统一时区，默认 Asia/Shanghai） |
| `.NN` | 当天第几次，两位，从 `01` 起 |

**适合**：Web 应用、SaaS、AI Agent、内部工具、需要频繁交付的项目。
**优点**：一眼知道“哪天发的、那天第几版”；不用纠结“这算 minor 还是 patch”。
**缺点**：不能表达“不兼容变更”；库的使用者无法从版本号判断升级风险。

#### 方案 B：语义化版本 `MAJOR.MINOR.PATCH`

```
1.4.2
├─ MAJOR：不兼容变更（用户必须改代码）
├─ MINOR：向下兼容的新功能
└─ PATCH：向下兼容的修复
```

tag 写作 `v1.4.2`；预发布 `v1.5.0-rc.1`（永不进生产）。

**适合**：npm 包、SDK、CLI、插件、应用商店上架的 App。
**缺点**：持续部署时，“这周到底发了哪版”不如日期号直观。

#### 怎么选

| 你的项目 | 选哪个 |
|---|---|
| Web / SaaS / AI 应用，随时部署 | **A（日期号）** |
| 开源库、SDK、CLI，别人依赖你 | **B（SemVer）** |
| 桌面/移动 App 上架 | **B + build number** |
| 给客户验收的交付项目 | **A**（方便对照交付日期） |
| 纯文档/内容站 | A 或日期，都行 |

> 不要两套混用。项目里只能有一个“发布号”方案。

### 3.2 单一真源与产物自证

**唯一真源**：仓库根目录的 `VERSION` 文件，只有一行。

```
R20261106.02
```

> `package.json` / `pyproject.toml` 里的版本号可以保留（工具链需要），但**不是交付版本的真源**：构建时从 `VERSION` 同步，或明确写“以 `VERSION` 为准”。不要让两处各改各的。

**构建时自动注入，禁止手写**：

```bash
# 构建脚本的第一段（日期号示例）
VERSION="$(cat VERSION)"
case "$VERSION" in
  R[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9].[0-9][0-9]) ;;
  *) echo "VERSION 格式不对: $VERSION" >&2; exit 1 ;;
esac
export APP_VERSION="$VERSION"
```

用 SemVer 时，把校验换成 `^[0-9]+\.[0-9]+\.[0-9]+`。

产物里必须带一份 `version.json`：

```json
{
  "version": "R20261106.02",
  "git_sha": "a77748d2",
  "built_at": "2026-11-06T18:00:00+08:00",
  "modules": { "web": "R20261106.02-web" },
  "schema": { "data": 3 }
}
```

**产物文件名带版本**：

```
dist/app-R20261106.02.tar.gz
MyApp-R20261106.02-mac.dmg
api-R20261106.02.jar
```

> 反例：`api-1.0.0.jar` 永远不变；`system.prev` 只有一份。这样无法回答“线上跑的是哪版”。

### 3.3 Git tag

- 用 **annotated tag**（`git tag -a`），不要 lightweight tag。
- tag 名 = `VERSION` 内容（SemVer 方案可加 `v` 前缀，全项目统一）。
- tag 打在**产生该产物的那个 commit** 上。
- 推送 tag：`git push origin <tag>`。
- 禁止改已推送的 tag；要改就发新版本。

```bash
V="$(cat VERSION)"
git tag -a "$V" -m "release $V
commit: $(git rev-parse --short HEAD)
notes: docs/releases/$V.md"
git push origin "$V"
```

### 3.4 模块版本（可选）

单仓库多模块（如 `web` / `core` / `api`）时：

```
<发布号>-<模块名>        例：R20261106.02-web
```

- 本次改了的模块用新发布号；没改的模块**继承旧号**。
- 记录在 `config/module-versions.json`，构建时读取。
- 小项目/单模块：**关掉**，只用发布号。

### 3.5 数据 schema 与配置版本

- 数据结构（数据库表、本地存储、文件格式）单独版本：`schema.data = 3`。
- 只前滚，不回滚：新代码要能读旧数据；旧代码读新数据至少不崩。
- 破坏性变更分两步：先加新字段（双写/兼容）→ 确认稳定 → 再删旧字段。
- 配置结构变更也要版本号（`config_version`），并在发布单记录。

### 3.6 版本号该出现 / 不该出现的地方

| ✅ 应该出现 | ❌ 不该出现 |
|---|---|
| `VERSION` 文件 | 目录名（`/opt/app-R20261106/`） |
| Git tag | 脚本名（`deploy-R20261106.sh`） |
| 发布单文件名 | 环境变量名（`R20261106_PORT`） |
| 产物文件名 | 端口号 |
| `version.json` / `/version` 接口 | 长期分支名 |
| 部署清单 `manifest.json` | 数据库表名 |
| 下载页展示 | 用户可见的 URL 路径 |

**版本号黑名单**（禁止出现在 tag、目录、文件名、发布单）：

```
latest  stable  final  new  v2  copy  副本  最终版  修改版
用 1.0.0 冒充交付版本（日期号方案里）  R2026-11-06  R20261106-1
R20261106.01-fix  R20261106.01-hotfix  R20261106.01-rollback
```

### 3.7 对账等式（发布前必须全过）

| # | 等式 | 怎么查 |
|---|---|---|
| E1 | `VERSION` 存在且格式正确 | `preflight` |
| E2 | tag 存在、是 annotated、指向发布 commit | `git cat-file -t <tag>` |
| E3 | 产物 `version.json.version` == `VERSION` | 解压/读取产物 |
| E4 | 发布单文件名 == `VERSION` | `test -f docs/releases/<V>.md` |
| E5 | 线上 `manifest.version` == 产物版本，文件哈希一致 | 部署后校验 |
| E6 | 工作区干净、`main` 已推送 | `git status --short` |

### 3.8 版本纪律

| 场景 | 规则 |
|---|---|
| 号已用过 | 永不复用，哪怕发到一半失败 |
| 同日多次 | `.01 .02 .03`，不写 `-hotfix` |
| 回滚 | **不产生新号**，把线上指回旧版本；旧版本必须还在 |
| 修复 | 发新号，不覆盖旧号 |
| 跳号 | 允许；没记录 = 没发生 |
| 预发布 | 可加 `-rc.1`（SemVer）或只在分支名体现（日期号）；永不进生产 |
| 只改文档 | 建议也发号（类型 `docs`），成本很低；也可由配置关闭 |
| 只改配置 | 发号，并在发布单写清改了哪个变量 |

## 4. 发布：先能退，再上线

### 4.1 先选节奏

| 节奏 | 适合 | 版本号 | 特点 |
|---|---|---|---|
| **连续发布**（默认） | Web/SaaS/AI 应用，单人 | 每次合并都可发一个号 | 小步、快、回滚容易 |
| **里程碑发布** | 有外部验收/应用商店/多人协作 | 每 1–2 周一个号 | 有冻结期、验收清单更长 |

连续发布不等于“每次提交都上线”。可以一天合并 5 次，但只在方便的时候发一次；**每次发布仍要完整走 §4.2–§4.4**。

### 4.2 发布前门禁（缺一不可）

| # | 检查 | 命令/证据 | 不过怎么办 |
|---|---|---|---|
| 1 | 工作区干净 | `git status --short` 为空 | 提交或 stash，别带着半成品发 |
| 2 | 在 `main` 且已同步 | `git pull --ff-only` | 先同步，再重跑 |
| 3 | CI 绿 | 最近一次流水线通过 | 修到绿，不许“上次绿” |
| 4 | 测试通过 | `npm test` / `pytest` / 等价命令 | 修，不许 skip |
| 5 | 构建通过 | `npm run build` | 修 |
| 6 | 版本对账 E1–E4 | `preflight --release` | 补 `VERSION`/tag/发布单 |
| 7 | 发布单草稿 | `docs/releases/<V>.md` | 先写“改了什么/怎么验/怎么回” |
| 8 | 回滚方案 | 目标版本 + 一条命令 + 数据影响 | 写不出来就不许发 |
| 9 | 备份（有状态系统） | 数据库/上传目录快照 + 校验 | 先备份 |
| 10 | 生产配置齐全 | 必填环境变量清单 | 缺一个都不发 |

> 门禁分两段跑：1–5、7–10 在构建前；第 6 项（含 tag）在构建、打 tag 后跑一次 `preflight --release`。任何一项 FAIL 就停，不要“先发再补”。

> **没有测试的项目**：至少要有“构建 + 启动 + 健康检查 + 一条核心路径”的冒烟脚本。不能用“我手动点过”代替。

### 4.3 发布步骤

> 顺序很重要：**先写并提交发布单 → 构建 → 打 tag → 自检 → 部署**。这样 tag 指向的提交既能构建出产物，也包含当次的记录。

```bash
# 0) 确认在 main、干净、最新
git switch main
git status --short          # 必须为空
git pull --ff-only

# 1) 写发布单草稿（先填 1–4、6、8、9；5、7 发布后补）
#    文件：docs/releases/$(cat VERSION).md

# 2) 提交发布单（让 tag 指向“既能构建、又包含记录”的提交）
git add "docs/releases/$(cat VERSION).md"
git commit -m "docs(release): $(cat VERSION)"

# 3) 构建（自动读取 VERSION，注入 version.json）
npm run build
test -f dist/version.json || { echo "缺少 version.json"; exit 1; }

# 4) 打包（文件名带版本）
tar -czf "dist/app-$(cat VERSION).tar.gz" -C dist .

# 5) 打 tag（指向刚刚构建的提交）
git tag -a "$(cat VERSION)" -m "release $(cat VERSION)"

# 6) 发布前自检（tag==HEAD、发布单、干净工作区、密钥/大文件）
bash docs/standards/scripts/preflight.sh --release

# 7) 部署（示例：替换软链，保留最近 3 个版本）
#    scripts/deploy.sh 内部应做：备份 → 上传 → 切换 → 健康检查 → 失败自动回滚

# 8) 验证
curl -fsS https://<你的域名>/health
curl -fsS https://<你的域名>/version    # 返回的 version 必须等于 VERSION

# 9) 推送 main + tag
git push origin main
git push origin "$(cat VERSION)"

# 10) 发布后：补发布单 5、7 的实际结果（新提交即可，不要移动 tag）
```

**发布过程中必须遵守**：

- 验证失败 = 发布失败，**立即停止**，不要“先清理再说”。
- 清理/删除类操作只在验证通过后执行。
- 生产只接受“从仓库某个 tag 构建的产物”；不许在服务器上改代码/改配置再重启。
- 同一次发布，构建一次、部署多次（多台机器用同一份产物）。

### 4.4 发布后验证（5 分钟）

1. `/health` 返回 200。
2. `/version` 返回的版本 == `VERSION`。
3. 首页/登录页能打开（关键入口）。
4. 一条核心业务路径能走通。
5. 日志里没有新的 ERROR/异常堆栈。
6. 静态资源 200（没有 404 的 JS/CSS）。
7. 移动端/目标浏览器抽一眼（如果适用）。
8. 观察 30 分钟；有告警/错误率上升就回滚。

### 4.5 发布单（9 项，缺一不可）

文件：`docs/releases/<版本>.md`，模板见 [`../../templates/release-note.zh.md`](../../templates/release-note.zh.md)。

| # | 项 | 写什么 |
|---|---|---|
| 1 | 基本信息 | 版本、时间（带时区）、类型 |
| 2 | 提交 | commit SHA、tag、分支 |
| 3 | 变更 | 一句话：谁的问题 → 改成什么；多模块分行 |
| 4 | 验证 | 跑了什么、结果、证据位置 |
| 5 | 构建/部署命令 | 原样贴，能复制执行 |
| 6 | 回滚 | 目标版本 + 一条命令 + 数据影响 |
| 7 | 风险/遗留 | 已知问题、监控点 |
| 8 | 数据/配置变更 | schema、环境变量、迁移步骤 |
| 9 | 影响范围 | 哪些模块/入口/用户受影响 |

禁止写法：「修复若干问题」「优化体验」「本地测过没问题」「最新代码」。

### 4.6 回滚剧本

**原则：先回滚，再排查。** 用户在看故障的时候，不要在现场调试。

```
发现异常
  ├─ 影响用户？ → 立即回滚到上一个验证过的版本
  ├─ 只影响新功能？ → 关闭功能开关（feature flag）
  └─ 数据被写坏？ → 停止写入 → 备份现场 → 回滚代码 → 单独修数据
```

**回滚前必须知道**：

- 目标版本号（上一个**验证过**的版本）。
- 一条可执行命令。
- 数据影响：这次发布有没有 schema 变更？旧代码能不能读新数据？
- 回滚后要不要重新构建（产物有没有保留）。

**回滚规则**：

1. 回滚**不产生新版本号**；线上指回旧版本，记录“回滚事件”。
2. 旧版本必须还在（保留最近 3 个产物/镜像）。
3. 代码可回滚，**数据只前滚**；需要修数据时单独脚本、单独审批。
4. 回滚后要发新号修复，不要“在旧版本上直接改”。
5. 每月在 staging 演练一次回滚，确认命令真的能跑。

### 4.7 热修复

```bash
# 1) 从出问题的 tag 切分支（不是从 main）
git switch -c hotfix/R20261106.02-login-500 R20261106.02

# 2) 最小改动 + 针对性测试 + 全量冒烟
# 3) 提交、合并回 main（不要直接 push 到 main）
# 4) 发新号（当天日期 + 下一个 NN），打 tag
# 5) 发布单类型写 hotfix，写清根因和防复发
```

- 热修复只修问题，不夹带新功能/重构。
- 修完必须回合并到 `main`，否则下次发布又把它带回来。
- 24 小时内补事故记录。

### 4.8 数据库与数据变更

| 规则 | 说明 |
|---|---|
| 迁移文件入库 | 放 `migrations/`，按序号命名，只追加 |
| 只前滚 | 不写 down 迁移（或写了也不用）；回滚靠兼容，不靠删数据 |
| 向后兼容一格 | 新代码能读旧数据；旧代码读新数据不崩 |
| 破坏性变更分两步 | 先加新字段并双写 → 稳定后再删旧字段 |
| 发布前备份 | 数据库快照 + 恢复演练记录 |
| 禁止手工改生产表 | 所有变更走迁移脚本；紧急修数据要单独脚本 + 审批 + 记录 |
| 大表变更 | 评估锁表时间，选低峰期，必要时用在线工具 |

### 4.9 出事故怎么办

1. **止损**（0–5 分钟）：回滚/关开关/限流，先让用户能用。
2. **记录**（5–15 分钟）：时间线、影响面、当前状态。
3. **修复**（15 分钟–数小时）：修根因，走正常发布流程。
4. **复盘**（24 小时内）：现象、影响、时间线、根因、处置、防复发。
5. **改进**（1 周内）：把防复发措施变成测试/门禁/文档，而不是“下次注意”。

事故记录不追责，但必须写“哪个门禁没拦住”。如果答案是“没有门禁”，就补一个。

### 4.10 什么时候不该发布

- 工作区不干净 / CI 没绿 / 回滚方案没写。
- 周五下班前 1 小时（除非是热修复）。
- 你困了、急了、同时在做三件事。
- 发布单写不出“改了什么”——说明你自己也没想清楚。
- 生产正在告警/有人在排障。
